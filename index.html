1. Criptografia Simétrica

A criptografia simétrica é o modelo em que emissor e receptor compartilham uma mesma chave secreta, usada tanto para cifrar quanto para decifrar. É a base dos algoritmos DES, 3DES e AES.

1.1 Cifras de Fluxo vs. Cifras de Bloco

Cifra de FluxoCifra de Bloco
UnidadeBit ou byte por vezBloco inteiro (64 ou 128 bits)
MecanismoXOR com fluxo de chaves pseudoaleatórioTransformação estruturada do bloco inteiro
IdealOne-time pad (inquebr. se chave verdadeiramente aleat.)AES (padrão moderno)
LimitaçãoFluxo precisa ser compartilhado via canal seguroMensagens longas exigem modos de operação
UsoTransmissão contínua, streamingArquivos, discos, redes, protocolos
Cifra de Fluxo: Chave ──▶ Gerador de fluxo ──▶ k₁ k₂ k₃ ... m₁ m₂ m₃ ... ──XOR──▶ c₁ c₂ c₃ ... Cifra de Bloco: Texto claro (bloco de 128 bits) ──▶ Algoritmo + Chave ──▶ Texto cifrado (128 bits)

1.2 Confusão e Difusão (Shannon)

Claude Shannon formulou dois princípios fundamentais para cifras seguras:

PrincípioObjetivoComo é implementado
DifusãoEspalhar a influência de cada bit do texto claro por muitos bits do texto cifrado; dissociar estrutura estatísticaPermutações, expansões, rotações de bits
ConfusãoTornar complexa a relação entre chave e texto cifrado; conhecer parte da saída não revela a chaveSubstituições não-lineares (S-boxes)

Exemplo matemático de difusão: para mensagem M = m₁, m₂, m₃, ...

  y_n = ( Σ m_(n+i), i=1..k ) mod 26

Onde k letras do texto claro influenciam cada letra do texto cifrado, aproximando as frequências do texto cifrado de uma distribuição uniforme.

Ponto-chave: Difusão ≠ Confusão

Difusão esconde padrões do texto claro — um único bit da entrada deve afetar muitos bits da saída. Confusão esconde a relação entre a chave e o texto cifrado, dificultando a recuperação da chave mesmo com acesso a muitos pares de texto claro/cifrado. Uma cifra de bloco segura precisa dos dois princípios combinados.

1.3 Rede de Feistel

A rede de Feistel é uma estrutura clássica para cifras de bloco que permite criar transformações reversíveis mesmo quando a função interna de rodada não é reversível. Foi proposta por Horst Feistel com base em Shannon (1945) e é usada no DES.

Estrutura de uma rodada

O bloco de entrada (2w bits) é dividido em metades L₀ e R₀. Para cada rodada i:

  L_i = R_(i-1)
  R_i = L_(i-1) ⊕ F(R_(i-1), K_i)
L_(i-1) R_(i-1) │ │ │ ┌────▼────┐ │ │ F(·,Kᵢ) │◀── Kᵢ (subchave) │ └────┬────┘ │ XOR ◀──────── L_(i-1) │ │ R_i = L_(i-1) L_i = R_(i-1)

A decriptação usa a mesma estrutura, apenas aplicando as subchaves em ordem inversa (K_n, K_(n-1), ..., K_1). Isso simplifica implementações em hardware.

Vantagens

  • A função F pode ser qualquer função — não precisa ser inversível.
  • Encriptação e decriptação usam o mesmo circuito.
  • Várias rodadas acumulam difusão e confusão progressivamente.

1.4 Parâmetros que Afetam a Segurança

ParâmetroEfeitoExemplo
Tamanho do blocoBloco maior → menos repetição de padrões; maior complexidadeDES: 64 bits; AES: 128 bits
Tamanho da chaveChave maior → mais resistente a força brutaDES: 56 bits (inseguro); AES: 128/192/256 bits
Número de rodadasMais rodadas → mais difusão acumulada; mais resistência à criptoanáliseDES: 16 rodadas
Escalonamento de chavesEscalonamento fraco permite relações previsíveis entre subchavesCada rodada usa subchave K_i derivada de K

1.5 DES — Data Encryption Standard

O DES foi o padrão dominante por décadas. Usa rede de Feistel com 16 rodadas, blocos de 64 bits e chave de 56 bits efetivos (64 bits totais, 8 bits de paridade não participam da criptografia).

Função de rodada do DES

R de 32 bits │ ┌────▼────┐ │ Expansão │ 32 → 48 bits └────┬────┘ │ XOR ◀──── Kᵢ (48 bits, subchave da rodada) │ ┌────▼────┐ │ 8 S-boxes │ 48 → 32 bits (substituição não-linear) └────┬────┘ │ ┌────▼────┐ │ Permutação │ └────┬────┘ │ f(R, Kᵢ)

O texto claro passa por uma permutação inicial, 16 rodadas Feistel e uma permutação final inversa. As S-boxes são o núcleo da confusão.

Por que o DES ficou inseguro

A chave de 56 bits gera 2⁵⁶ ≈ 7,2 × 10¹⁶ possibilidades. Com hardware moderno e paralelismo, um ataque de força bruta torna-se viável. A estrutura conceitual do DES (Feistel, S-boxes, avalanche) continua importante para estudo, mas não deve ser usado em produção.

1.6 Efeito Avalanche

O efeito avalanche é uma propriedade desejável: uma pequena alteração na entrada (um único bit) deve causar uma grande alteração na saída — idealmente, cerca de metade dos bits de saída deve mudar.

Texto claro A: 10110010 ... ──▶ Cifra ──▶ Cifrado A Texto claro B: 10110011 ... ──▶ Cifra ──▶ Cifrado B (1 bit diferente) (muitos bits diferentes)

Esse efeito impede que atacantes façam previsões sobre a saída baseados em pequenas variações da entrada. Alcançado pelo acúmulo de difusão ao longo das rodadas.

1.7 Triple DES (3DES)

O 3DES surgiu como solução de transição, aumentando a segurança do DES sem abandoná-lo. Aplica o DES três vezes na sequência EDE (Encripta–Decripta–Encripta):

  C = E_K3 ( D_K2 ( E_K1 (P) ) )

O uso da decriptação no meio não tem a função de "desfazer" a cifra — foi escolhido para manter compatibilidade com sistemas DES antigos (se K1 = K2 = K3, o 3DES se comporta como DES simples). Com K1 = K3 ≠ K2, obtém-se 112 bits de segurança efetivos.

O 3DES é mais lento que o AES e foi substituído em novos sistemas. Está depreciado na maioria dos padrões modernos.

1.8 AES — Advanced Encryption Standard

O AES, baseado no algoritmo Rijndael, foi selecionado pelo NIST em 2001. Diferentemente do DES, o AES usa uma rede de substituição-permutação (SPN), não Feistel.

VarianteTamanho de blocoTamanho de chaveRodadas
AES-128128 bits128 bits10
AES-192128 bits192 bits12
AES-256128 bits256 bits14

Operações internas por rodada: substituição de bytes (SubBytes), deslocamento de linhas (ShiftRows), mistura de colunas (MixColumns), adição da chave de rodada (AddRoundKey). Para prova conceitual, o essencial é que AES substituiu o DES como padrão moderno com blocos de 128 bits e chaves muito maiores.

Claude Shannon (1945) │ ▼ cifras de produto ┌────────────┬──────────────────────┐ │ Rede de Feistel SPN │ │ DES → 3DES Rijndael → AES│ └────────────┴──────────────────────┘

1.9 Modos de Operação: ECB, CBC, CTR, GCM

Uma cifra de bloco opera sobre blocos de tamanho fixo. Para mensagens longas, é necessário um modo de operação que defina como os blocos são encadeados.

ModoIdeiaProblema
ECBCifra cada bloco independentementeBlocos iguais produzem cifrados iguais — vaza padrões. Inseguro para dados estruturados.
CBCXOR do bloco claro com bloco cifrado anterior antes de cifrar; usa IV no primeiro blocoSequencial (não paralelizável); erros propagam; IV deve ser imprevisível.
CTRCifra uma sequência de contadores (nonce + contador) e combina com a mensagem por XORNão oferece autenticação; nonce não pode ser reutilizado com a mesma chave.
GCMCTR + autenticação GHASH; gera uma tag de autenticação sobre o texto cifradoImplementação incorreta pode ser catastrófica; nonce único essencial.
ECB: P₁ ──▶ E_K ──▶ C₁ P₂ ──▶ E_K ──▶ C₂ (independente) CBC: IV ──XOR── P₁ ──▶ E_K ──▶ C₁ ──XOR── P₂ ──▶ E_K ──▶ C₂ CTR: (nonce||ctr₁) ──▶ E_K ──XOR── P₁ ──▶ C₁ (nonce||ctr₂) ──▶ E_K ──XOR── P₂ ──▶ C₂ GCM: CTR acima ──▶ texto cifrado GHASH(texto cifrado + AAD, H) ──▶ tag de autenticação
Por que o ECB não deve ser usado?

Se dois blocos de texto claro são idênticos, seus blocos cifrados também são idênticos no ECB. Isso revela padrões estruturais da mensagem. O exemplo clássico é cifrar uma imagem bitmap no modo ECB: as áreas uniformes da imagem original continuam visíveis no resultado cifrado, porque regiões com a mesma cor produzem o mesmo bloco cifrado.

2. Funções Hash, MACs e Assinaturas Digitais

2.1 Função Hash

Uma função hash recebe uma mensagem de tamanho variável M e produz um valor de tamanho fixo:

  h = H(M)

O valor h é chamado de hash, digest ou resumo. A função adiciona padding quando a entrada não é múltipla do tamanho desejado. Propriedades gerais:

  • Saída deve parecer aleatória e ser uniformemente distribuída.
  • Efeito avalanche: pequena mudança em M altera bastantes bits de h.
  • Objetivo primário: verificação de integridade.

Propriedades de Hash Criptográfico

  • Mão única (one-way): dado h, é computacionalmente inviável encontrar M tal que H(M) = h.
  • Livre de colisão: inviável encontrar M₁ ≠ M₂ tais que H(M₁) = H(M₂).
  • Computacionalmente inviável de quebrar com eficiência maior que força bruta.

2.2 Integridade com Hash e o Problema da Autenticação

Verificação de integridade

  1. Emissor calcula h = H(M).
  2. Emissor transmite M + h.
  3. Receptor recalcula H(M_recebido) e compara com h recebido.
  4. Divergência → mensagem ou hash adulterada.

Problema: um adversário (man-in-the-middle) pode interceptar, alterar M e recalcular h. Hash simples não garante autenticidade.

Soluções:

MétodoDescrição
A. Hash + cifragem simétrica do parConcatena M + H(M) e cifra tudo com chave simétrica.
B. Apenas hash cifradaCifra somente H(M) com chave simétrica; válido quando confidencialidade não é exigida.
C. Hash sobre M + segredoH(M ∥ segredo). Adversário não tem o segredo; base do HMAC.
D. Método C + confidencialidadeAplica C e também cifra o par M + tag.

2.3 MAC e HMAC

Um MAC (Message Authentication Code) é uma função de hash chaveada. Recebe (chave secreta K + mensagem M) e produz uma tag de autenticação. Apenas quem conhece K pode produzir ou verificar o MAC.

O HMAC (Hash-Based MAC) constrói o MAC a partir de uma função hash criptográfica e uma chave, seguindo o método C acima:

  HMAC(K, M) = H( (K ⊕ opad) ∥ H( (K ⊕ ipad) ∥ M ) )

Usos: autenticação de mensagens entre partes com chave compartilhada, verificação de integridade em protocolos (TLS, IPsec).

Limitação do MAC: é simétrico — ambas as partes têm a mesma chave e podem gerar MACs válidos. Portanto, não oferece não repúdio: Bob não pode provar a terceiros que foi Alice quem gerou o MAC.

2.4 Assinaturas Digitais

A assinatura digital usa criptografia assimétrica: o emissor assina com sua chave privada e qualquer pessoa pode verificar com a chave pública correspondente. Na prática, assina-se o hash da mensagem, não a mensagem inteira.

MecanismoUsa chave?IntegridadeAutenticidadeNão repúdio
Hash simplesNãoSimNãoNão
MAC / HMACSim (secreta)SimSimLimitado
Assinatura digitalSim (par assimétrico)SimSimSim
Hash simples: Mensagem ──▶ H(M) ──▶ Digest MAC/HMAC: Mensagem + Chave secreta ──▶ H(K ∥ M) ──▶ Tag Assinatura digital: Mensagem ──▶ H(M) ──▶ E_privado(H(M)) ──▶ Assinatura Verificação: D_publico(Assinatura) == H(M_recebido) ?

Assinatura com confidencialidade

Para confidencialidade + autenticação: Alice assina com sua chave privada, depois cifra tudo com a chave pública de Bob. Bob decifra com sua chave privada e verifica a assinatura com a chave pública de Alice.

Outros usos de hash

  • Senhas de mão única: sistemas armazenam H(senha), nunca a senha em texto claro. Para segurança real, usa-se também salt (valor aleatório por usuário) para impedir tabelas pré-computadas.
  • Detecção de intrusão e malware: hashes de executáveis do sistema são monitorados; alteração indica comprometimento.

2.5 Resistências e Paradoxo do Aniversário

PropriedadePergunta que o atacante tenta responderCusto esperado
Pré-imagemDado h, encontrar x tal que H(x) = hO(2ⁿ)
Segunda pré-imagemDado x, encontrar y ≠ x com H(y) = H(x)O(2ⁿ)
ColisãoEncontrar qualquer par x ≠ y com H(x) = H(y)O(2^(n/2))

O paradoxo do aniversário explica por que colisões são mais baratas: em uma sala com 23 pessoas, há >50% de chance de duas fazerem aniversário no mesmo dia (de 365 possibilidades). Para um hash de n bits, a chance de colisão é significativa com apenas ~2^(n/2) tentativas — um hash de 128 bits oferece apenas ~64 bits de segurança contra colisões.

Definições: pré-imagem vs. colisão

Pré-imagem: entrada da função hash; x tal que h = H(x). Resistência à pré-imagem = impossível inverter h para encontrar x.

Colisão: ocorre se existir x ≠ y tal que H(x) = H(y). Colisões matematicamente existem (domínio infinito → codomínio finito), mas devem ser computacionalmente inviáveis de encontrar.

2.6 SHA e SHA-512

A família SHA (Secure Hash Algorithm) é o padrão mais usado de funções hash criptográficas. O SHA-512 produz um digest de 512 bits e processa a mensagem em blocos, mantendo um estado interno atualizado por várias rodadas. SHA-256 (256 bits) é amplamente usado em TLS, certificados e blockchain.

Para prova conceitual: o essencial é saber que SHA garante resistência à pré-imagem, segunda pré-imagem e colisão, e que a família SHA é o padrão atual (SHA-1 está depreciado; SHA-2 e SHA-3 são seguros).

3. Criptografia Assimétrica, RSA e Diffie-Hellman

3.1 Ideia de Chave Pública

A criptografia de chave pública (assimétrica) introduz um par de chaves: uma pública (distribível) e uma privada (secreta). Resolve dois problemas da criptografia simétrica:

  • Distribuição de chaves: não é necessário um canal seguro prévio para compartilhar chave.
  • Assinaturas digitais: permite não repúdio, impossível com chave simétrica.
ObjetivoQuem cifra / assinaQuem decifra / verifica
ConfidencialidadeAlice usa chave pública de BobBob usa sua chave privada
Autenticação/assinaturaAlice usa sua chave privadaQualquer um usa chave pública de Alice

Mitos: a criptografia assimétrica não é intrinsecamente mais segura que a simétrica (depende do tamanho da chave e custo computacional) e não a substitui — as duas são complementares.

Funções de mão única com alçapão

A base da criptografia assimétrica é a função de mão única com alçapão (trapdoor one-way function): fácil de calcular em uma direção, inviável de inverter sem a informação secreta (o alçapão). No RSA, o alçapão é a fatoração de n = p·q em seus primos; na posse dos primos, é simples calcular a chave privada.

PKI — Infraestrutura de Chave Pública

A PKI (Public Key Infrastructure) é o conjunto de políticas, processos e plataformas para administrar certificados e pares de chaves: emissão, manutenção e revogação de certificados. Um certificado de chave pública é um documento emitido e assinado digitalmente com a chave privada de uma CA (Autoridade Certificadora), vinculando um nome a uma chave pública.

3.2 RSA

O RSA (Rivest, Shamir, Adleman) é o criptossistema de chave pública mais importante. Pode cifrar, decifrar, assinar e verificar assinaturas.

Geração de chaves

  1. Escolhe-se dois primos grandes p e q.
  2. Calcula-se n = p·q e φ(n) = (p−1)·(q−1).
  3. Escolhe-se e tal que mdc(e, φ(n)) = 1 → chave pública PU = {e, n}.
  4. Calcula-se d tal que e·d ≡ 1 (mod φ(n)) → chave privada PR = {d, n}.

Operações

  Cifragem:    C = Mᵉ mod n
  Decifragem:  M = Cᵈ mod n

  Assinatura:  S = H(M)ᵈ mod n
  Verificação: H(M) == Sᵉ mod n ?

A entrada n normalmente usa 2048 bits (blocos de ~616 dígitos) em implementações seguras. Exemplos didáticos usam n pequeno — não representam segurança real.

Segurança do RSA

A segurança depende da dificuldade de fatorar n em p e q. Se um atacante fatorar n, recalcula φ(n) e obtém d. Como algoritmos e poder computacional evoluem, tamanhos de chave devem ser escolhidos com margem (≥ 2048 bits atualmente; 4096 bits para segurança a longo prazo).

3.3 Diffie-Hellman

O Diffie-Hellman não cifra mensagens — é um protocolo de acordo de chaves: permite que dois lados estabeleçam uma chave secreta comum por meio de um canal público.

Protocolo (parâmetros públicos: primo q e gerador α)

Alice Bob ───────────────────────────────────────────────────────── Escolhe segredo X_A Escolhe segredo X_B Calcula Y_A = α^X_A mod q Calcula Y_B = α^X_B mod q │ │ └──────── troca pública de Y_A, Y_B ─────┘ │ │ K = Y_B^X_A mod q K = Y_A^X_B mod q (mesma chave K = α^(X_A·X_B) mod q)

Segurança: Logaritmo Discreto

A segurança do DH depende da dificuldade do logaritmo discreto: dado α, q e Y = α^x mod q, é computacionalmente inviável recuperar x quando os parâmetros são grandes. Um atacante pode ver Y_A e Y_B, mas não consegue obter X_A, X_B nem a chave K.

3.4 Ataque Man-in-the-Middle no Diffie-Hellman

O DH básico não autentica os participantes. Um atacante no meio pode:

  1. Interceptar Y_A e Y_B.
  2. Estabelecer uma chave K₁ com Alice (fingindo ser Bob).
  3. Estabelecer uma chave K₂ com Bob (fingindo ser Alice).
  4. Descriptografar, ler e re-criptografar tudo que passa.
Alice ◀── DH (K_AM) ──▶ Atacante ◀── DH (K_MB) ──▶ Bob Alice pensa estar falando com Bob. Bob pensa estar falando com Alice.

Solução: autenticar os valores DH trocados com assinaturas digitais e certificados. Em protocolos reais (TLS, IKE), o acordo de chaves combina DH com autenticação.

Ponto-chave: RSA pode cifrar e assinar; Diffie-Hellman estabelece chave compartilhada mas precisa de autenticação adicional.

4. IPsec

O IPsec é um conjunto de protocolos de segurança para a camada de rede (camada 3). Protege datagramas IP e pode operar entre hosts, roteadores ou entre host e roteador. Principal aplicação: criação de VPNs sobre a Internet pública.

Pilha com TLS: Pilha com IPsec: Aplicação (HTTP, DNS, etc.) Aplicação TLS TCP/UDP TCP IPsec + IP IP Enlace Enlace TLS protege conexões de aplicação. IPsec protege datagramas IP — transparente para as aplicações.

IPsec e VPNs

Uma VPN (Virtual Private Network) permite que redes privadas comuniquem-se com segurança por rede pública. Em uma VPN site-to-site, roteadores de borda encapsulam e protegem pacotes. Em uma VPN de acesso remoto, dispositivos individuais estabelecem túneis até a rede da organização.

4.1 AH e ESP

AHAuthentication HeaderNãoSimSimQuando confidencialidade não é necessária
ESPEncapsulating Security PayloadSimOpcionalOpcionalVPNs — o mais usado na prática

O ESP em modo típico oferece confidencialidade + autenticação + integridade e é o protocolo preferido em instalações modernas.

4.2 Associação de Segurança (SA)

Uma SA (Security Association) é uma relação lógica unidirecional que define como proteger o tráfego IPsec em uma direção. Contém:

  • SPI (Security Parameter Index) — identificador único.
  • Algoritmos e chaves a usar.
  • Tempo de vida e contadores anti-replay.

Para comunicação segura bidirecional entre dois hosts, são necessárias duas SAs (uma por sentido). Em uma VPN com muitos clientes, o número de SAs cresce rapidamente.

No modo túnel, os roteadores de borda conhecem o IPsec, mas os hosts internos não precisam. O datagrama original fica totalmente escondido no interior do novo pacote.

4.5 IKE — Internet Key Exchange

O IKE é o protocolo de gerenciamento de chaves do IPsec. Sem ele, seria necessário configurar manualmente chaves e SAs, o que não escala. O IKE automatiza:

  • Autenticação mútua das partes.
  • Negociação de algoritmos e parâmetros.
  • Estabelecimento de chaves (usando Diffie-Hellman).
  • Criação e renovação de SAs.
IKE Fase 1 ──▶ Cria canal seguro (IKE SA) │ ▼ IKE Fase 2 ──▶ Negocia e cria SAs IPsec (AH/ESP)

5. TLS — Transport Layer Security

O TLS protege comunicações de aplicações sobre TCP, adicionando confidencialidade, integridade e autenticação de ponto final. É o protocolo por trás do HTTPS, entre outros.

TLS é o sucessor do SSL. Sistemas modernos usam TLS; "certificado SSL" é um termo histórico que persiste no vocabulário cotidiano.

5.2 Sessão TLS vs. Conexão TLS

Várias conexões TLS podem reutilizar uma sessão TLS, evitando o custo do Handshake completo (que envolve operações assimétricas caras) em cada reconexão.

5.3 TLS Record Protocol

O Record Protocol processa dados das camadas superiores:

  1. Fragmenta os dados em blocos.
  2. (Opcional) Comprime.
  3. Calcula proteção de integridade (MAC ou AEAD).
  4. Cifra o resultado.
  5. Transmite com cabeçalho de tipo e versão.

No receptor, o processo é invertido. A proteção depende das chaves e algoritmos acordados no Handshake. Após o Handshake, usa-se criptografia simétrica (AES-GCM, por exemplo) — muito mais eficiente que assimétrica.

5.5 Heartbeat e Heartbleed

Heartbeat

A extensão Heartbeat permite verificar se a outra parte ainda está ativa sem renegociar a conexão (mecanismo keep-alive). Uma parte envia uma mensagem com um payload e o tamanho declarado; a outra deve responder ecoando o mesmo payload.

Heartbleed (CVE-2014-0160)

Vulnerabilidade na implementação da extensão Heartbeat no OpenSSL. O problema: o servidor não validava se o tamanho declarado da mensagem correspondia ao payload real. Um atacante enviava um payload de 4 bytes declarando tamanho de 64 KB — o servidor lia 64 KB da sua própria memória e retornava.

Normal: Cliente: tamanho=4, dados="ABCD" ──▶ ◀── "ABCD" Heartbleed: Cliente: tamanho=65535, dados="ABCD" ──▶ ◀── "ABCD" + 65531 bytes de memória do servidor

Impacto: a memória retornada podia conter chaves privadas, cookies de sessão, senhas, dados de outros usuários. O ataque era silencioso (sem rastros claros em logs) e simples de executar.

Lição: usar protocolos criptográficos corretos não é suficiente. A implementação também precisa ser correta, validada e mantida atualizada.

Hash vs MACHash não usa chave e não autentica origem. MAC usa chave secreta e autentica a mensagem entre partes que compartilham a chave.

7. Perguntas de Revisão

Cifras de Bloco

1. Qual é a diferença entre cifra de fluxo e cifra de bloco?

Cifras de fluxo processam a mensagem bit a bit ou byte a byte, combinando com um fluxo de chaves pseudoaleatório via XOR. Cifras de bloco pegam blocos inteiros (64 ou 128 bits) e aplicam uma transformação estruturada sobre todo o bloco. DES, 3DES e AES são cifras de bloco; para mensagens longas, usam-se modos de operação (ECB, CBC, CTR, GCM).

2. O que significam confusão e difusão? Por que a cifra de bloco precisa dos dois?

Difusão: cada bit do texto claro deve influenciar muitos bits do texto cifrado — impede deduções estatísticas (um bit muda → metade dos bits da saída muda). Confusão: a relação entre chave e texto cifrado deve ser tão complexa que conhecer parte da saída não revele informação sobre a chave — implementada com substituições não-lineares (S-boxes). Sem difusão, padrões do texto claro aparecem no cifrado. Sem confusão, a chave pode ser inferida.

3. Por que a rede de Feistel permite usar o mesmo circuito para encriptação e decriptação?

Em cada rodada Feistel: L_i = R_(i-1) e R_i = L_(i-1) ⊕ F(R_(i-1), K_i). Para decriptar, aplica-se as mesmas operações mas com as subchaves em ordem inversa. A função F pode ser qualquer função — não precisa ser invertível, porque ela nunca é aplicada "ao contrário"; usa-se XOR para desfazer seu efeito. Isso simplifica hardware e software.

4. Por que o DES é inseguro e por que o modo ECB não deve ser usado?

O DES tem chave efetiva de 56 bits (2⁵⁶ possibilidades). Com hardware moderno e computação paralela, um ataque de força bruta é viável. O ECB é inseguro porque cifra cada bloco independentemente: se dois blocos de texto claro forem iguais, seus cifrados também são iguais, revelando padrões estruturais da mensagem (o exemplo clássico é uma imagem bitmap cujas regiões uniformes continuam visíveis após cifração com ECB).

5. O que o GCM adiciona em relação ao CTR?

O CTR transforma a cifra de bloco em cifra de fluxo cifrando contadores e combinando com a mensagem por XOR. Oferece apenas confidencialidade. O GCM (Galois/Counter Mode) combina o CTR com uma função de autenticação (GHASH), produzindo uma tag de autenticação sobre o texto cifrado. Com GCM, qualquer alteração no texto cifrado é detectada — oferece AEAD (Authenticated Encryption with Associated Data): confidencialidade + integridade em uma única operação.

Hash, MAC e Assinaturas

6. Hash simples garante autenticidade? Por quê?

Não. Hash simples garante apenas integridade acidental (detecta corrupção). Qualquer pessoa pode calcular hash — um adversário que intercepta a mensagem pode alterá-la, recalcular o hash e reenviar o par modificado. Para autenticidade é necessário um segredo: MAC (chave simétrica compartilhada) ou assinatura digital (chave privada).

7. Qual a diferença entre MAC e assinatura digital?

O MAC usa chave secreta simétrica — ambas as partes têm a mesma chave, então qualquer uma pode gerar MACs válidos. Isso impede não repúdio: Bob não pode provar a terceiros que o MAC veio de Alice, porque ele próprio podia tê-lo gerado. A assinatura digital usa chave privada para assinar e chave pública para verificar. Como apenas o dono conhece a chave privada, a assinatura oferece não repúdio forte: qualquer terceiro pode verificar a assinatura com a chave pública.

8. Por que o paradoxo do aniversário é relevante para segurança de funções hash?

Ataques de colisão são muito mais baratos que ataques de pré-imagem. Para uma hash de n bits, encontrar uma pré-imagem custa O(2ⁿ), mas encontrar uma colisão genérica custa apenas O(2^(n/2)) pelo paradoxo do aniversário. Portanto, um hash de 128 bits oferece apenas 64 bits de segurança contra colisões — insuficiente para usos modernos. Isso motivou o uso de SHA-256 (128 bits de segurança contra colisões) e SHA-512 (256 bits).

Criptografia Assimétrica

9. Como a criptografia de chave pública resolve o problema de distribuição de chaves?

Na criptografia simétrica, emissor e receptor precisam compartilhar uma chave secreta previamente por um canal seguro — o que é difícil em escala. Com chave pública, cada usuário publica sua chave pública livremente. Qualquer um pode cifrar com a chave pública do destinatário; só o destinatário (com sua chave privada) consegue decifrar. Não é necessário canal seguro prévio para trocar a chave de cifragem.

10. Por que o Diffie-Hellman básico é vulnerável a man-in-the-middle?

O DH permite que duas partes derivem uma chave comum trocando valores públicos, mas não autentica quem enviou esses valores. Um atacante pode interceptar Y_A e Y_B, substituí-los pelos seus próprios valores e estabelecer duas chaves separadas: uma com Alice e uma com Bob. Cada parte acredita estar falando com a outra, mas na verdade o atacante decifra, lê e re-cifra toda a comunicação. Solução: autenticar os valores DH com assinaturas digitais e certificados (como fazem TLS e IKE).

IPsec e TLS

11. O que é uma SA e por que ela é unidirecional?

Uma SA (Security Association) é uma relação lógica que define como proteger o tráfego IPsec em uma única direção: define algoritmos, chaves, SPI e parâmetros anti-replay para aquele sentido de comunicação. É unidirecional porque os parâmetros (algoritmos, chaves, contadores) de A→B podem ser diferentes dos de B→A. Para comunicação bidirecional segura entre dois hosts, são necessárias duas SAs — uma para cada sentido.

12. Qual é a diferença entre SAD e SPD?

O SPD (Security Policy Database) armazena políticas: dado um datagrama, o que fazer? As opções são: proteger com IPsec, descartar ou deixar passar. O SAD (Security Association Database) armazena os parâmetros das SAs ativas: chaves, algoritmos, SPI, contadores. O fluxo de decisão é: consulta SPD para decidir o que fazer → se for necessário IPsec, consulta SAD para saber como aplicá-lo.

13. Por que o Heartbleed foi tão grave?

O Heartbleed explorava a extensão Heartbeat do OpenSSL: o código não validava se o tamanho declarado do payload correspondia ao payload real. Um atacante podia enviar 4 bytes mas declarar 64 KB, fazendo o servidor retornar 64 KB de sua própria memória. Essa memória podia conter chaves privadas TLS, cookies de sessão, senhas e dados sensíveis de outros usuários. O ataque era silencioso (sem rastros claros), simples de executar e afetava grande parte da infraestrutura HTTPS global. A lição: a implementação de protocolos criptográficos precisa ser tão rigorosa quanto o protocolo em si.

14. Qual a diferença entre sessão TLS e conexão TLS?

Uma sessão TLS é uma associação mais ampla entre cliente e servidor, criada pelo Handshake, que contém parâmetros criptográficos (algoritmos, segredos derivados) que podem ser reutilizados por múltiplas conexões futuras — evitando o custo de um novo Handshake completo (operações assimétricas). Uma conexão TLS é o canal transitório peer-to-peer efetivamente usado para transmitir dados protegidos. Várias conexões podem compartilhar uma única sessão.
