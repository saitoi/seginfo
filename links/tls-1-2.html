Lista 7 — TLS: respostas detalhadas, arquitetura e handshake completo

0. Visão geral

O TLS — Transport Layer Security — é um protocolo usado para fornecer segurança entre duas aplicações que se comunicam pela rede. O exemplo mais comum é o HTTPS, isto é, HTTP protegido por TLS. Porém, o TLS não é exclusivo do HTTP: ele pode proteger qualquer protocolo de aplicação que opere sobre TCP, como SMTP, IMAP, FTP, LDAP, entre outros.

Seu objetivo principal é impedir três problemas centrais em comunicações pela Internet:

  1. Escuta indevida: um atacante intercepta os dados e lê informações sensíveis.
  2. Modificação em trânsito: um atacante altera os dados sem autorização.
  3. Falsificação de identidade: um servidor falso se passa pelo servidor legítimo.

Para resolver isso, o TLS combina:

  • criptografia simétrica, para proteger grandes volumes de dados com eficiência;
  • criptografia assimétrica, para autenticação e troca segura de segredos;
  • certificados digitais, para provar a identidade do servidor;
  • MAC ou AEAD, para integridade e autenticação dos registros;
  • handshake, para negociar algoritmos, chaves e parâmetros antes dos dados da aplicação.

O TLS fica logicamente entre a aplicação e o TCP. Tecnicamente, ele é implementado como uma camada de segurança acima do transporte confiável fornecido pelo TCP. Para a aplicação, o TLS se comporta de forma parecida com um socket TCP, mas com serviços adicionais: sigilo, integridade e autenticação.

Esse diagrama representa o handshake completo TLS 1.2, incluindo mensagens obrigatórias e opcionais. As mensagens opcionais dependem do CipherSuite escolhido e da necessidade ou não de autenticação do cliente.

Descrição detalhada e enumerada do Diagrama 1.2

Camadas e entidades envolvidas

  1. Aplicação Cliente (APP_C): software que deseja utilizar uma conexão segura, como um navegador Web.
  2. Cliente TLS (C): implementação TLS responsável por handshake, criptografia, autenticação e proteção dos dados.
  3. Servidor TLS (S): implementação TLS do lado servidor.
  4. Aplicação Servidor (APP_S): aplicação protegida pelo TLS, como um servidor HTTP.
  5. TCP: camada de transporte confiável utilizada pelo TLS.
  6. TLS Record Protocol: camada responsável por transportar todas as mensagens TLS.
  7. Handshake Protocol: protocolo responsável pela negociação de parâmetros de segurança.
  8. Change Cipher Spec Protocol: protocolo responsável por ativar os parâmetros criptográficos negociados.
  9. Alert Protocol: protocolo responsável por erros, avisos e encerramento da conexão.
  10. Heartbeat Extension: extensão opcional para verificação de vivacidade da conexão.

Fase 0 — Preparação da conexão

  1. A aplicação cliente solicita uma conexão segura ao cliente TLS.
  2. Antes do TLS iniciar, uma conexão TCP já deve estar estabelecida.
  3. O TLS passa a utilizar esse canal TCP para transportar suas mensagens.

Fase 1 — Iniciação e negociação de capacidades

Passo 1: ClientHello

  1. O cliente envia a mensagem ClientHello.

  2. Essa mensagem é transportada pelo TLS Record Protocol.

  3. O cliente informa:

    • versão máxima suportada;
    • valor aleatório client_random;
    • identificador de sessão;
    • lista de CipherSuites suportadas;
    • métodos de compressão;
    • extensões TLS.
Passo 2: ServerHello

  1. O servidor responde com ServerHello.

  2. O servidor escolhe:

    • versão TLS;
    • CipherSuite;
    • método de compressão;
    • identificador de sessão.

  3. O servidor envia também seu valor aleatório server_random.

Resultado da Fase 1

  1. Cliente e servidor passam a compartilhar:

    • versão TLS;
    • CipherSuite;
    • método de compressão;
    • Session ID;
    • client_random;
    • server_random.

Fase 2 — Autenticação do servidor e parâmetros de chave

Passo 3: Certificate

  1. O servidor envia seu certificado digital X.509.

  2. O certificado contém:

    • identidade do servidor;
    • chave pública;
    • assinatura da autoridade certificadora.
Passo 4: ServerKeyExchange (opcional)

  1. Dependendo da CipherSuite, o servidor envia parâmetros adicionais.

  2. Exemplo:

    • parâmetros Diffie-Hellman efêmeros;
    • parâmetros ECDHE.

  3. Esses parâmetros normalmente são assinados digitalmente.

Passo 5: CertificateRequest (opcional)
  1. Caso deseje autenticação mútua, o servidor solicita certificado do cliente.
Passo 6: ServerHelloDone
  1. O servidor informa que terminou suas mensagens iniciais.
  2. O controle passa para o cliente.
Resultado da Fase 2

  1. O cliente possui todas as informações necessárias para:

    • autenticar o servidor;
    • validar certificados;
    • preparar a troca de chaves.

Fase 3 — Resposta do cliente e estabelecimento do segredo compartilhado

Passo 7: Validação do certificado

  1. O cliente verifica:

    • cadeia de certificação;
    • assinatura da CA;
    • validade temporal;
    • nome do servidor;
    • uso permitido da chave.
Passo 8: Certificate (opcional)
  1. Se solicitado, o cliente envia seu certificado.
Passo 9: ClientKeyExchange

  1. O cliente envia material de chave.

  2. Dependendo da CipherSuite:

    • envia um pre_master_secret cifrado com RSA;
    • ou envia parâmetros públicos Diffie-Hellman/ECDHE.
Passo 10: CertificateVerify (opcional)

  1. Se o cliente enviou certificado com capacidade de assinatura:

    • assina o transcript do handshake;
    • prova posse da chave privada.
Passo 11: Derivação de chaves

  1. Cliente e servidor calculam:

    • pre_master_secret;
    • master_secret;
    • key_block.

  2. A partir do key_block são derivadas:

    • chaves de criptografia;
    • chaves de MAC;
    • IVs;
    • parâmetros de leitura e escrita.
Resultado da Fase 3
  1. Ambos possuem exatamente os mesmos segredos criptográficos.

Fase 4 — Ativação dos parâmetros criptográficos

Passo 12: ChangeCipherSpec do cliente
  1. O cliente envia ChangeCipherSpec.
  2. Essa mensagem pertence ao Change Cipher Spec Protocol.
  3. Ela informa que os próximos registros usarão as novas chaves.
Passo 13: Finished do cliente
  1. O cliente envia Finished.
  2. Essa é a primeira mensagem protegida pelas novas chaves.
  3. Ela verifica a integridade de todo o handshake.
Passo 14: ChangeCipherSpec do servidor
  1. O servidor ativa seus parâmetros criptográficos.
Passo 15: Finished do servidor
  1. O servidor envia sua mensagem Finished.
  2. O cliente verifica a mensagem recebida.
Resultado da Fase 4
  1. O handshake é concluído.
  2. A conexão TLS passa para o estado operacional.

Fase 5 — Troca de dados da aplicação

Passo 16: Application Data

  1. A aplicação cliente envia dados.

  2. O TLS Record Protocol:

    • fragmenta;
    • autentica;
    • cifra;
    • encapsula os dados.

  3. O servidor recebe e decifra os registros.

  4. Os dados são entregues à aplicação servidora.

Passo 17: Resposta da aplicação
  1. O mesmo processo ocorre no sentido inverso.

Fase 6 — Encerramento da conexão

Passo 18: Alert Protocol

  1. Quando a comunicação termina, uma das partes envia:

    close_notify

  2. Essa mensagem pertence ao Alert Protocol.

  3. A outra parte responde com seu próprio close_notify.

  4. O encerramento ocorre de forma limpa e segura.

Fase 7 — Heartbeat (opcional)

Passo 19: HeartbeatRequest

  1. Caso a extensão tenha sido negociada, uma das partes envia:

    HeartbeatRequest
Passo 20: HeartbeatResponse

  1. A outra parte responde:

    HeartbeatResponse
Objetivos
  1. Verificar se a conexão continua ativa.
  2. Evitar encerramento por inatividade em NATs e firewalls.
  3. Manter sessões longas sem necessidade de renegociação.
